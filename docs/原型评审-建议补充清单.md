# 中药房 PDA 原型评审：建议补充清单

> 评审对象：`dispenseVerify` 移动端原型（uni-app + Vue3，8 个页面，`src` 与 `standalone/pharmacy-pda.html`）
> 评审口径：按要求**忽略已对接的接口实现细节**，只看「静态/演示数据」和「页面交互与业务代码逻辑」，回答"还该加什么"。
> 本次**未修改任何代码**。日期：2026-11-17。

---

## 〇、先说三个必须知道的事实（会改变你判断优先级）

### 1. 当前实际跑的是静态数据，不是真实接口

`src/services/data-source.js` 只有一行：

```js
export const useStaticData = true
```

`prescription.js` 里 `if (useStaticData) return staticPrescription(path, data)` —— **所有请求都被静态数据拦截**，真实 HTTP 分支根本不执行。

所以 README 第 3 行"src 已改为调用真实业务接口，不再读取演示处方"与代码**不符**。文档和代码打架时，以代码为准。这决定了：**静态数据不是"演示用的旧东西"，它现在就是唯一在跑的东西**，值得认真补。

### 2. standalone HTML 和 src 是同源的，不是旧版

`standalone/pharmacy-pda.html`（189K）由 `scripts/export-single-html.mjs` 从当前 8 个页面编译导出，内含接口改造后的文案和全部演示患者，没有 src 之外的页面/字段/交互。README 说它"未重新导出"也不准。**两份是同一套东西**，改哪边都要注意另一边。

### 3. 前端调 12 个接口，后端只有 6 个（最影响后续的一条）

| 前端在调 | 后端有吗 |
|---|---|
| `/pharmacy/acceptance/page` `/acceptance/confirm` `/dispense/page` `/dispense/confirm` `/dispense/today` `/scan/resolve` | ✅ 有（我实测 8 个全注册） |
| `/pharmacy/acceptance/today` | ❌ **不存在** |
| `/pharmacy/outpatient/visit/start` `/outpatient/prescription/verify`（门诊双扫码） | ❌ **不存在** |
| `/pharmacy/ward-receive/page` `/confirm` `/today`（住院病区接收） | ❌ **不存在** |

也就是说：**门诊"双扫码发药"和住院"病区接收"这两条主流程，前端逻辑写得最完整，但后端没有对应接口**。这不是代码 bug，是前后端契约没对齐。你后面补静态数据、做演示、定验收标准时，必须把这三组标成"待后端确认/可能要做接口"，否则演示跑通了、真机上全是 404。

## 一、最该补：静态数据缺一整类"拦截场景"

README 白纸黑字写了这三个演示样本，但 `static-prescription.js` 里**根本不存在**：

| README 声称 | 实际 |
|---|---|
| `PKG-CANCELLED` 已退方 | ❌ 数据里搜不到 |
| `PKG-WITHDRAWN` 已撤回 | ❌ 数据里搜不到 |
| `PKG-FOREIGN` 其他医院 | ❌ 数据里搜不到 |

代码里 `statusLabels` 定义了 `cancelled/withdrawn`，`blockedReason` 也写了一堆拦截规则，但**没有任何一条数据能触发它们**。结果是：所有拦截逻辑（已退方、已撤回、跨医院、非自取、登记号不一致、HIS 未映射）在演示中永远走不到，等于没验证过。

**建议补 6~8 条"坏样本"处方**，每条专门触发一种拦截：

| 补什么 | 触发什么 | 验证哪段代码 |
|---|---|---|
| 已退方处方 | 验收/发药都被挡，提示"已退方" | `acceptPackage` / `dispensePackage` 的 status 拦截 |
| 已撤回处方 | 同上，提示"已撤回" | 同上 |
| 其他医院处方 | 提示"不属于本院，禁止操作" | `hospitalId !== ctx.body.hospitalCode` |
| 非自取处方（快递到家） | 门诊 PDA 不能验收/发药 | `pickupType` 判断 / `FYFSLX` |
| 登记号不一致的药包 | 双扫码核对失败 | `verifyPrescription` 比对 |
| 需要 HIS 映射的就诊码 | 提示"尚未完成 HIS 映射" | `requiresHISMapping` 分支 |
| 一个执行批次下 2~3 个物理药包 | 必须扫具体药包码 | 拆分批次 + `packageCode` 逻辑 |
| 历史日期处方（3 天前） | "全部日期"搜索能查到 | 日期过滤 |

这 8 条补完，原型的"业务严谨性"才演示得出来——**这是投入产出比最高的一件事**。

## 二、补"今日/历史"时间维度数据

现在 14 条处方的所有时间都是**当天 08:00~09:25**（代码里 `at()` 用 `new Date()` 拼当天）。导致：

- 首页"最近两天"和"全部日期"标签看不出区别（`filter-chip` 写了但没数据支撑）；
- 三个明细页的"全部"按钮是禁用的，永远只能看今日；
- 无法演示"历史处方也能验收"（requirements 已明确这条规则，但没数据）。

**建议**：给处方加 `prescriptionDate` 分布——今天 5 条、昨天 4 条、3 天前 3 条、7 天前 2 条。这样"最近两天 / 全部日期"的差异立刻可见，也呼应了 requirements 第 6 项待确认点。

## 三、把"死控件"接上逻辑，或明确标注

评审发现两个纯展示、没有任何点击效果的控件：

1. **发药页 `filter-line` 的 4 个 chip**（`全部日期/最近两天`、`配送自取`、`代煎自取`、`当前患者`）——现在是 `<text>` 不是 `<button>`，点不动。
2. **三个明细页 `RecordList` 的"全部"按钮**——`disabled`，无历史查询。

**建议二选一**：
- 若它们是目标功能：接上筛选逻辑（用第一节的历史日期 + `pickupType` 数据就能做），静态模式下很容易实现；
- 若暂时不做：在旁边加一行灰字"筛选功能开发中"，别让演示者以为坏了。

## 四、修掉"名实不符"：病区接收页实际在发药

`ward-receive/index.vue` 页面标题、按钮、列表都叫"接收"，但 `confirm()` 和 `confirmSelected()` 实际调用的是 **`dispensePackage()`（发药）**，`receivePackage()`（真正的病区接收确认）定义了却**没有任何页面调用**，成了死代码。

交接文档说这是"新规则：病区一致后直接确认发药，不串联逐包接收"，那**文案就该跟着改**：

- 页面名、按钮改成"病区核对发药"，别叫"病区接收"；
- 或者保留"接收"语义，把 `receivePackage()` 接回来，做"接收 → 发药"两步。

现在这种"叫接收、干发药"的状态，业务人员看演示会理解错流程。

---

## 五、"我的"页太单薄，README 承诺的模拟事件没了

`profile/index.vue` 现在只有人员信息 + 几行状态文案，**没有任何按钮和事件**。但 README 第 38 行说这里有"HIS / 短信模拟事件"，交接文档说已移除——文档又打架了。

**建议**（静态演示模式下值得加）：
- 一个"模拟事件"列表：每笔验收/发药产生一条 HIS 回传事件 + 一条短信提醒事件（时间、处方号、类型、状态、重试按钮）；
- 一个"清空演示数据"按钮：现在数据只在内存，刷新即丢，但加个显式入口更好演示；
- 一个"查看当前会话"折叠区：展示 hospitalCode / wardCode / operatorId / mode —— 这样演示跨医院拦截、病区切换时能看到上下文，排查"为什么被拦"特别有用。

## 六、页面级状态补齐（错误态 / 空态 / 重试）

| 页面 | 现状 | 建议 |
|---|---|---|
| 首页 | `recent` 为空时一片空白，无 loading / 空态 | 加骨架屏或"暂无今日操作"空态 |
| 各页 `refresh()` | 失败只 `toast`，页面停留在旧状态或空白 | 加页面级错误条 + "重试"按钮 |
| 批量提交 | 部分失败只在行内红字，无汇总入口 | 加"重试失败的 N 条"按钮 |
| 扫码失败 | 只有通用输入框兜底 | 加明确引导："可手动输入药包码/处方号" |

## 七、演示与真实行为不一致的地方（会误导演示者）

1. **门诊"批量发药"**：静态模式下放行（`manual && useStaticData`），真实接口模式被拦截（"门诊仅支持双扫码发药"）。演示时看起来支持批量，真机上报"不支持"。建议静态模式也按真实规则拦，或在按钮上标"仅演示"。
2. **短信勾选**：交接文档说"保留但禁用"，但 `accept/index.vue` 的 checkbox 只绑了 `:disabled="submitting"`，两种模式都能勾。既然后端没有短信接口（后面会问），建议显式禁用并标"待接口"。
3. **审计时间用客户端时钟**：静态数据 `at()` 用 `new Date()`。演示无妨，但要在页面底部常驻提示"演示时间为本机时间，生产以服务端为准"，避免截图被当成真实记录。

## 八、跟"后端能力"对齐后再补的数据/字段

这几条虽然属于接口范畴，但**决定了静态数据该长什么样**，所以列在这里：

1. **验收明细接口不存在**（`/pharmacy/acceptance/today` 后端没有）——首页"今日已验收"和验收明细页在接口模式下拿不到数据。静态数据可以补，但要标"该接口待后端提供"。后端现成的替代是 `/hospital-acceptance/query`（按运单号查本医院验收记录），但没有"今日全部"的查询。
2. **双扫码 / 病区接收接口不存在**——门诊"就诊码识别→药包核验"和住院"逐包接收"两套逻辑在后端没有对应实现。静态数据里 `staticSession` 能造 `STATIC-n` token，但这是前端自嗨。建议把这两组流程的演示数据单独归一类，文件名或注释标清"依赖待建接口"。
3. **字段契约缺口**：静态数据里有 `ingredients`（药味）、`route`、`frequency`、`acceptedByName`、`smsSent` 等字段，但后端 `/pharmacy/*` 的 `map()` 返回里**没有** `ingredients` 和 `acceptedByName`（只有 `acceptedAt`、`dispensedByName`）。也就是说"处方药味明细"和"验收人姓名"在真实模式下会显示空/`--`。建议：要么让后端补字段，要么静态数据也别展示这两项，别造成"演示有、上线无"。
4. **多字段搜索方式不一致**：前端 `searchDispense()` 对 5 种 `searchType` 并发查 5 次再合并，但后端 `PharmacyRequest` 只有一个 `keyword` 字段、没有 `searchType`。静态数据模仿了多字段，真实模式会变成同一个关键词查 5 遍。建议确认后端是否支持 `searchType`，不支持就前端只查一次。

## 九、优先级建议（先做什么）

| 优先级 | 事项 | 理由 |
|---|---|---|
| **P0** | 第一节 8 条拦截类坏样本 + 第三节死控件处理 | 投入最小、验证价值最大，直接决定"业务规则演示得出来" |
| **P0** | 第三节"后端只有 6 个接口"的标注 | 不标清楚，后面联调必翻车 |
| **P1** | 第二节历史日期数据 + 第五节"我的"模拟事件 | 让"最近两天/全部""HIS/短信"这些需求点能演示 |
| **P1** | 第四节病区接收名实不符 + 第七节演示真实不一致 | 避免业务方理解错流程 |
| **P2** | 第六节页面级错误态/空态/重试 | 体验优化，可跟真实接口联调一起做 |
| **P2** | 第八节字段契约对齐 | 依赖后端确认，先记录不开发 |

## 十、一句总结

原型的**主流程交互已经做得相当细**（双扫码核对、上下文切换清数据、防重复提交、病区校验、分页拉取都有），缺的不是"再画几个页面"，而是：

1. **没有坏样本** —— 一堆拦截规则写了却验证不了；
2. **没有时间维度** —— "最近两天/历史"是空话；
3. **几个控件是死的、命名是错的** —— 演示会误导；
4. **前后端接口对不齐** —— 12 个前端接口里 6 个后端没有，这是最大的隐藏风险。

把 1、2、3 补上，原型就能完整演示"验收→发药"的所有正反向场景；第 4 条需要在联调前跟后端确认，否则静态演示越漂亮，真机落差越大。
