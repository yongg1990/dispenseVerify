## 请求与配置

- 请求封装：`src/services/prescription.js`。
- 页面数据适配和业务调用：`src/domain/pharmacy.js`。
- 全部使用 POST、JSON；默认接口根地址 `/api/prescription`。
- `VITE_PRESCRIPTION_API_BASE` 可设置完整网关地址或相对前缀，须包含 `/api/prescription` 对应实际前缀。配置示例在根目录 `.env.example`，真实部署值未提供，未写入示例医院或病区。
- 同域部署由网关转发 `/api/prescription`；跨域部署需后端允许对应 Origin、凭据和鉴权头。当前 Vite 配置没有擅自添加未知后端代理。
- 默认携带 Cookie（`withCredentials`）。登录系统可向 `uni` 存储键 `pharmacy-pda-session` 写入当前登录上下文：

```js
uni.setStorageSync('pharmacy-pda-session', {
  hospitalCode: '实际医院编码',
  hospitalName: '实际医院名称',
  wardCode: '当前授权病区编码',
  wardName: '当前授权病区名称',
  operatorId: '当前登录人员ID',
  operatorName: '当前登录人员姓名',
  department: '当前科室',
  authorization: '系统实际使用的完整Authorization值',
  headers: { /* 系统所需的其他鉴权头，无需时不传 */ }
})
```

- Cookie 登录可以不传 `authorization`。项目原先没有登录/SSO实现，附件也未提供身份上下文接口，本次仅预留上述入口，没有虚构登录接口。
- 环境变量 `VITE_HOSPITAL_CODE`、`VITE_HOSPITAL_NAME`、`VITE_WARD_CODE`、`VITE_WARD_NAME` 可提供部署默认值，登录上下文优先；不能据此前端值认定已授权，实际权限由服务端校验。
- 缺医院编码时阻止请求；病区接口缺病区编码时阻止请求；医院、人员、业务或登录鉴权上下文变化后清空旧数据。
- `code !== 0`、HTTP失败、网络失败均提示错误，不标记成功。报错优先显示接口非空 `msg`，其次 `message`；外层没有时读取 `data` 中的消息，均无有效消息才显示前端兜底。`code=0` 但业务标志未通过时同样保留接口错误消息，通用“成功/操作成功/请求成功/success/ok”不作为错误提示。纯前端参数校验及无接口响应的网络错误使用本地提示。命令请求没有自动重试。
- 分页接口每页100条，依据服务端 `pages`/`total` 顺序加载全部分页，保持现有无分页控件页面的列表使用方式。

## 保留的页面步骤与接口适配边界

1. 门诊仍是“识别患者 → 选择处方并在原弹层核对 → 确认发药”。没有重新设计页面。核对使用处方核验接口，原“药包核对”文案和弹层布局未重做；第二扫实际需使用医院处方二维码。
2. 选处方只决定待核对对象，不能绕过服务端第二扫。扫码核验失败时清除凭证并回到患者识别步骤。离开页面也清除凭证；有效期由服务端决定。
3. 住院保留原 `ward-receive` 页面及入口，扫码核验病区相同后直接确认发药。按钮使用真实住院发药接口，不再调用病区接收确认，不再增加二次患者核对或全部药包接收的前端条件。
4. 门诊和住院首页明细均指向发药明细 `dispense-records`，读取对应业务的 `/dispense/today`。接收明细独立页面仍保留，但不再作为发药明细菜单目标。
5. 各提交入口增加请求中锁，避免异步请求重复点击。前端不伪造服务器时间、操作人、HIS回执、短信成功状态。
6. H5 不再从模拟处方弹出二维码选择器；使用现有输入框接收PDA键盘型扫码枪的原始文本。App扫码仍调用 `uni.scanCode`。未添加新的摄像头或厂商SDK。
